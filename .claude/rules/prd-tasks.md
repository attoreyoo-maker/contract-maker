# PRD.md·tasks.md 고치거나 점검할 때 규칙

- `idea/` 파일이나 대화 중 사용자가 명시적으로 정한 내용으로 추적할 수 없는 기능·화면·수용 기준을 새로 넣지 마세요. 근거가 없으면 `(질문 필요)`라고 표시하고 지어내지 말고 물어보세요.
- 사용자는 `PRD.md`에 반복적으로 8줄짜리 점검표를 적용합니다 (사용자 스토리 모양, 스토리의 누구가 페르소나와 일치, 스토리 개수 == 넣을 기능 개수, 수용 기준 모양이 "누르면 → 화면에 무엇이 보인다"인지, 잘/편하게/빠르게/제대로/깔끔하게 같은 흐린 말이 없는지, 수용 기준의 버튼·칸 이름이 사용자 흐름에 있는지, 넣을 기능마다 수용 기준이 1개 이상 있는지, 넣을 기능이 3개 이하이고 비목표 줄마다 까닭이 있는지). 이 점검표 실행을 요청받으면 줄 단위로 통과/걸림만 보고하고, 고쳐 달라는 요청이 없으면 고치지 마세요.
- **제품 기획 연습** (`idea/`, `PRD.md`, `tasks.md`) — 사용자는 학습자로서, 작은 웹 앱 아이디어("계약서 만들기" — 혼자 온라인 쇼핑몰을 운영하는 자영업자를 위한 계약서 자동 생성 도구)를 원시 메모에서 PRD로, 다시 구현 체크리스트로 다듬어가는 중입니다. 아직 앱 코드는 존재하지 않으며, 요구사항 정의 단계입니다.
- `idea/` — 앱 아이디어에 대한 원시 제품 정의 메모(`topic.md`, `user.md`, `scope.md`, `ipo.md`, `flow.md`, 와이어프레임 이미지, 그리고 초기 브레인스토밍 파일인 `ideas.md`, `problems.md`, `shortlist.md`). 이 파일들이 `PRD.md`에 들어갈 내용의 *유일한* 근거입니다 — 여기 없는 기능이나 화면을 지어내지 마세요.
- `PRD.md`(루트)는 오직 `idea/` 폴더 파일들을 근거로 작성되고, `tasks.md`(루트)는 오직 `PRD.md`를 근거로 만든 구현 체크리스트입니다. 둘 중 하나를 이어서 작업할 때는 다음을 지키세요.
- `PRD.md`는 정해진 순서를 따릅니다: 문제(배경/목표) → 사용자(페르소나/사용자 스토리) → 범위(넣을 기능/기능 요구사항/비목표) → 화면(사용자 흐름, 머메이드 흐름도 포함) → 완성 기준(수용 기준).
- 와이어프레임이 정한 화면 개수는 고정인데 기능을 다 넣으면 "넣을 기능 3개 이하" 기준을 넘게 되는 경우, 화면이나 기능을 빼기보다 화면 하나당 관련 세부 기능들을 넣을 기능 한 줄로 묶는 방식을 우선하세요 — 이 프로젝트에서 이미 써온 방식입니다.
- `tasks.md`는 `PRD.md`의 화면 1/2/3에 맞춰 화면별로 할 일을 묶고, 화면에서 눈으로 확인 가능한 단위마다 `- [ ] ...` 한 줄로 적고, 그 할 일이 채우는 수용 기준 번호를 괄호로 답니다. `PRD.md`의 모든 수용 기준은 할 일 하나 이상과 연결되어야 하며, 연결 안 된 것이 있으면 알려주세요.
